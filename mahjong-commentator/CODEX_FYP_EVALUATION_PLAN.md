## 1. Why this plan is needed

The project parses Mahjong game logs into per-discard records (commonly `decisions.json`), calculates shanten/ukeire and alternative-discard evidence in Python, and calls local LLMs (e.g., Qwen3:8b and DeepSeek-R1:8b) to explain decisions in Traditional Chinese.

**Earlier prototype:** An LLM received game-state/evaluator information and wrote the full four-part commentary. This produced hallucinations, including wrong shanten descriptions, retained/discarded-tile contradictions, invented tiles, invalid Mahjong terminology, and unsupported strategic comparisons.

**Recent Codex-assisted version:** Python generates most of the numerical commentary and handles fallback text. The LLM returns a constrained JSON explanation with fields such as `comparison`, `reason_codes_used`, and `explanation`. This improves control but risks reducing the LLM to a slow template paraphraser. It also risks making metrics misleading if Python-corrected outputs are scored as though they were raw model output.

**Core research tension:** Reliability versus genuinely useful explanation. We need to test whether an LLM contributes strategic understanding or educational value **above a deterministic Python baseline**, rather than assuming that valid JSON or copied numbers make an LLM valuable.

### Concrete observed examples

**Example A — same actual/recommended discard:** One recorded Qwen3:8b response had approximately **20,635 ms latency**, valid JSON, and the explanation:

> 「實際棄牌與推薦棄牌均達成相同向聽數及入章數，故評估器判定兩者效率相等。」

Its reason codes were `SAME_SHANTEN`, `SAME_UKEIRE`, `ACTUAL_EQUALS_RECOMMENDATION`. The actual and recommended discarded tiles were identical. This sentence is factually straightforward and could be generated in Python. **This is not evidence of independent LLM reasoning.** The distinction between `same_action` and `equal_efficiency_distinct_actions` should be preserved.

**Example B — different discards tied on efficiency:** An attached `decisions.json` example has actual discard `F` (發) and best-efficiency-listed discard `3s`; **both are 3-shanten with ukeire 27**, and both appear in `equally_efficient_discards`. There is no established efficiency winner. Additional metadata includes `shanten_by_type`, `ukeire_by_type`, candidate block decompositions, and discarded-tile yaku/dora metadata. A possible yakuhai route is *not* proof that retaining 發 is strategically best. Treat the first-ranked tile as an ordering choice within a tie, not as an objective strategic superiority claim.

**Earlier qualitative results:** A preliminary comparison over three consecutive decisions found errors in both Qwen3:8b and DeepSeek-R1:8b. Three consecutive samples are for debugging, **not** a representative comparison. If `mahjong_llm_preliminary_evaluation.md` is present, read it and reconcile its terminology with the actual code.

### Important boundaries

- `decisions.json` is authoritative for **what the evaluator reports**, not automatically for correct Mahjong strategy. Audit evaluator correctness independently.
- Shanten and ukeire measure tile efficiency, **not overall decision quality**. Strategy can involve yaku legality/availability, dora, defense, score, round context, hand value, and opportunity costs.
- RAG retrieves *general* strategy/rule knowledge; it does not magically compute state-specific discard quality, valid yaku, or calibrated deal-in risk.
- An LLM can explain **plausible evidence-supported reasons**, but should not pretend to know why Mortal or a human actually chose a move without evidence.
- A fallback can improve the **product's** factual reliability while masking the **raw model's** limitations. Score both separately.

## 3. Evaluation design — compare the correct things

### 3.1 Evaluation units

- **Decision:** A specific 14-tile discard situation, with full game context and candidate evaluations.
- **Response:** One model output for a decision, before validation or fallback.
- **Atomic claim:** An independently assessable proposition, e.g., “Discarding 3s keeps 3-shanten,” “Both choices have ukeire 27,” or “Discarding F removes a possible yakuhai development route.”
- **Gold insight:** A manually reviewed, strategically or educationally relevant insight which a useful explanation should cover. Gold insights must be grounded in the available evidence and should be labeled as verified fact, supported conditional interpretation, or not assessable.
- **Production response:** The final user-visible result after validation and optional Python fallback; distinguish it from raw LLM output.

### 3.2 Proposed metrics and precise definitions

| Metric | Proposed operational definition | Source / scoring | Caveats |
|---|---|---|---|
| **Factual Precision (FP)** | `correct_verifiable_claims / all_verifiable_claims_assessed` | Claim extraction plus Python checking, with human adjudication when needed | Unsupported/unknown does not automatically mean factually false. Report eligibility count. |
| **Evidence Support Rate (ESR)** | `supported_assessable_claims / all_assessable_evidence-claim_units` | Evaluator/game-state evidence, retrieved passages if present, human/validated judge labels | Distinguish `supported`, `contradicted`, `not_supported_by_available_evidence`, and `not_assessable`. Decide denominator before experiments. |
| **Comparative Relevance (CR)** | `supported, decision-discriminating comparative claims / all assessed comparative claims` | Pairwise actual-vs-alternative annotations | A correct explanation of a tie is relevant; shared properties must not be described as advantages. If no comparative claims exist, N/A; also evaluate whether comparison was *needed but omitted*. |
| **Comparison Verdict Accuracy (CVA)** | `correct comparison labels / decisions with assessable comparison target` | Python evaluator `(shanten, -ukeire)` and gold case classification | Suggested labels: `same_action`, `equal_efficiency_distinct_actions`, `actual_more_efficient`, `alternative_more_efficient`, `insufficient_evidence`. Efficiency verdict ≠ overall strategic verdict. |
| **Atomic Recall (AR)** | `gold insights correctly covered / total applicable gold insights` | Small human-annotated gold set; optionally an adjudicated semantic matcher | Do not define gold solely by shanten/ukeire if testing strategic value. |
| **Incremental Insight Coverage (IIC)** | `gold insights covered by LLM but NOT by Python baseline / total gold insights` | Paired, same-decision annotation of Python and LLM outputs | Also report **net recall gain** = `AR_LLM - AR_Python`; IIC and net gain measure different things. |
| **Unsupported Claim Rate (UCR)** | `unsupported_or_contradicted_claims / all_assessed_claims` | Claim labels; additionally report contradicted and merely unsupported separately | A long verbose model can make more claims; report count per response as well as rate. |
| **Format Compliance (FC)** | `schema-valid and required-fields-compliant raw responses / all raw responses` | JSON schema/parser, enumerated values, required fields | Valid JSON != factually accurate. |
| **Generation Latency (GL)** | Wall-clock time for inference, measured consistently | Model-call timer; median, p90, max; optional token counts | Keep hardware, warmup, output budget, and decoding settings comparable. Separate extraction/validation and end-to-end latency. |
| **Fallback Rate (FR)** | `responses replaced/corrected by Python / total responses` | Validator/fallback logs | A system can have perfect final FP but high fallback rate, indicating limited usable LLM output. |
| **Extraction Coverage (EC)** | `target claims successfully extracted / manually labeled target claims` | Human-labeled extraction sample | Prevent regex/claim extractors from inflating FP by ignoring difficult claims. |

**No eligible claims:** report `N/A` plus counts; do not silently treat empty denominators as 100% or 0%.

**Macro vs micro:** Report micro-aggregated claim-level metrics (across eligible claims) **and** per-decision macro means when possible. Otherwise long responses can dominate results. Include 95% intervals only if sample size and resampling assumptions are defensible; small pilot results are descriptive.

**Judge reliability:** If an LLM judge performs semantic claim extraction or support labeling, manually audit a sample, distinguish judge error from generator error, and report agreement. Never use unvalidated LLM-judge scores as ground truth.

**Metric scoping:** FP/ESR/UCR and claim counts belong to **raw** outputs when evaluating models. Report the same metrics on **final system output** separately, with FR and repair latency. Do not combine both into one headline score.

### 3.3 Do not conflate these two comparison targets

1. **Efficiency comparison** — objective under the evaluator's explicit algorithm: shanten, ukeire, and tie rules.
2. **Strategic comparison** — may depend on legal yaku, defense, current hand value, riichi threats, relative scores, etc. Without those features, label conclusions as tentative or `insufficient_evidence`.

A model that declines to make an unsupported strategic recommendation may be *better grounded* than a model that confidently picks a winner.

## 4. Candidate experiments / ablations

Keep test decisions, prompts, evidence access, inference settings, and scoring rules reproducible. Distinguish experimental treatments instead of changing everything at once.

| ID | System / ablation | Main question |
|---|---|---|
| **A — Python baseline** | Python template from evaluator; no LLM | How useful is the deterministic system by itself? |
| **B — Free-form grounded LLM** | Same evidence, but LLM writes explanation without pre-scripted reasoning | Does the model add insight, and what hallucinations appear? |
| **C — Structured grounded LLM** | LLM returns schema-constrained JSON and its *own* explanation; Python only validates | Does structure reduce hallucinations without collapsing into template paraphrase? |
| **D — Validated production pipeline** | C plus validation and fallback; save raw and final outputs | How much reliability improvement is due to correction, and at what cost? |
| **E — RAG extension (later)** | C plus retrieved Mahjong rule/strategy passages | Does retrieval add accurate strategic/educational insight over C? |
| **F — Enriched strategic evidence (later)** | C plus yaku, dora, riichi/defense, or Mortal evidence | Does state-specific strategic evidence matter more than RAG alone? |

**Important design caveat:** A versus B is a *system comparison*; for model-to-model comparisons, compare the same B or C treatment across Qwen3:8b / DeepSeek-R1:8b (and optionally smaller models). C versus D isolates effects of repair. E/F are future work, not required for this meeting.

**Optional control:** For structured models, compare (i) copying canned reason codes into prose against (ii) selecting contextually relevant facts and expressing an explanation in original words. If both yield equivalent usefulness, the extra LLM invocation may not be justified for static commentary.

### 4.1 Dataset proposal

**Immediate pilot:** approximately 20–30 diverse decisions *if available*; hand-annotate a smaller subset (for example 10–15) with 2–3 key insights per decision. Existing three consecutive turns are debugging examples only.

Cover at least:

1. Same actual and recommended discard (`same_action`).
2. Different discards with equal shanten and ukeire.
3. Same shanten, different ukeire.
4. Different shanten / hand-route alternatives, including Chiitoitsu.
5. Dora or possible-yaku trade-off where evidence is available.
6. Defense/riichi situations **only if the log and evaluator support valid labels**.
7. Examples of invalid/overlapping block evidence and difficult structural explanations.

Prefer decisions from different games, rounds, and shanten levels. Consider grouping by game for later uncertainty estimates to avoid assuming adjacent turns are independent.

### 4.2 Minimum annotation schema (proposal, not mandated implementation)

```json
{
  "decision_id": "gameA_round2_turn4",
  "efficiency_verdict": "equal_efficiency_distinct_actions",
  "gold_insights": [
    {
      "id": "g1",
      "text": "Both candidates have the same shanten and ukeire under this evaluator.",
      "status": "verified",
      "source": "evaluator"
    },
    {
      "id": "g2",
      "text": "The evaluator alone does not establish a strategic winner.",
      "status": "verified",
      "source": "comparison_scope"
    }
  ],
  "notes": "Human-reviewed; do not infer offensive/defensive superiority without data."
}
```

## 6. Possible outcomes and challenges (HYPOTHESES, not actual results)

| Potential observation | Interpretation | Challenge / follow-up |
|---|---|---|
| Python baseline has highest factual precision, but limited insight coverage | Deterministic facts are reliable; explanation usefulness may need generative synthesis | Human gold insights must cover more than copied numbers |
| Free-form LLM has more insight but more unsupported statements | Generation offers breadth at the cost of grounding | Investigate structured evidence, selective generation, verification |
| Structured LLM is as accurate as Python but adds almost no insights | LLM is a paraphraser in the present task | Consider static template baseline or move LLM to interactive Q&A |
| Qwen and DeepSeek differ on format/latency but not substantive insight | Model selection may be dominated by compute cost | Control token/output budgets; report uncertainty, don't overclaim |
| Post-validation achieves high final precision but high fallback rate | Reliability comes mostly from Python | Report raw FP and fallback rate; don't credit model with repaired claims |
| RAG improves rules explanations but not state-specific choice | General knowledge is not a strategy engine | Add explicit strategic state features; test retrieved passage relevance |
| RAG increases confident but unsupported recommendations | Retrieved advice does not imply applicability to this game state | Evidence attribution, applicability checks, abstention |
| Better annotations reveal “correct but irrelevant” statements | Copy accuracy is not sufficient | Use CR, AR, IIC, human relevance and actionability ratings |
| Evaluator contains bugs or ambiguous block decompositions | “Ground truth” may be wrong or misleading | Independent reference checks; separate evaluator errors from LLM errors |
| Pilot differences are small or inconsistent | Data too small or heterogeneous for model ranking | Present descriptive results; expand / stratify later |

### Specific risks to call out

- **Leaky scoring:** Evaluating reason codes largely authored by Python and calling the result LLM performance.
- **Fallback contamination:** Scoring corrected final text as if the raw model produced it.
- **Trivial metric ceilings:** Identical-discard decisions can be solved entirely with templates.
- **Invalid denominators:** Counting unverifiable strategic advice as automatically false, or ignoring unextracted hard claims.
- **Tie mislabeling:** Treating first-ranked efficiency discard as uniquely better when `equally_efficient_discards` includes another.
- **Source-of-truth confusion:** `decisions.json` can provide correct *reported* metrics and still contain evaluator bugs.
- **Strategy overclaiming:** Low shanten does not guarantee legal winning yaku, good expected value, or a safe decision.
- **RAG attribution:** General strategy documents may be correct yet inapplicable to a particular board state.
- **Compute fairness:** Local model latency depends on tokens, context length, quantization, GPU offload, warmed caches, and output style.
- **Annotation ambiguity:** Several explanations may be useful and valid; gold atoms must not force a single unjustified “correct” strategic story.

## 9. Definitions and terminology to preserve

- `shanten` / 向聽: 0 is tenpai; 1-shanten is **not** tenpai.
- `ukeire` / 有效進張、入章數: number of remaining tiles improving the evaluated shanten objective, under the chosen visibility-count convention.
- `regular`, `chiitoitsu` (七對子), `kokushi` (國士無雙): distinct hand-shape routes.
- `equally_efficient_discards`: discards tied under the specific efficiency criterion; not necessarily equivalent strategically.
- `dora` / 赤寶牌: bonus han; dora alone does **not** satisfy the yaku requirement.
- `yakuhai` / 役牌: seat/round winds or dragons under applicable rules. An isolated yakuhai tile signals only a possible future route, not a confirmed yaku.
- `candidate_decomposition`: one of multiple possible non-overlapping groupings; **not** an exhaustive description of all possible pairs and complex shapes.
- `supported` vs `contradicted` vs `unsupported` vs `not_assessable`: distinct labels; do not merge them silently.

## 10. Project north star

**Research question:** *Can evidence-grounded local LLMs produce more strategically relevant and educational Riichi Mahjong discard explanations than a rule-based baseline, while preserving factual reliability? What do structured grounding, model selection, validation, and eventually RAG contribute?*

The strongest result is not necessarily “LLM wins.” A valid conclusion may be that Python templates are preferable for static numerical summaries, whereas LLMs become useful for selective strategic explanation or interactive tutoring. The experiments should be able to support **either** outcome.
